# LED-164 · Memoise rows so long lists stay smooth — retro (2026-09-28)

## What shipped
- `TransactionRow` wrapped in `React.memo`. Its `tx` prop was already reference-stable across a scroll/window-growth render (callers memoise `filtered`/`grouped`, and `sliceGroups` reuses the same group/item objects for unaffected rows); memoising the row alone would have done nothing, because its callback props were still fresh closures on every render.
- `useTransactions.ts`'s `deleteTransaction` wrapped in `useCallback` — the only one of the hook's mutations passed straight into a row. It was a plain function redefined on every render of the *owning page*, including a pure window-growth render, which would have defeated the row's memoisation regardless.
- `AccountTransactionsPage.tsx` and `TransactionsPage.tsx`: `handleDelete` wrapped in `useCallback`; `TransactionsPage.tsx` also wraps `toggleSelect` and a new `handleSaveTemplate` (replacing an inline `onSaveTemplate` closure) — the two other per-render-fresh closures reaching `TransactionRow` on that page.

## Acceptance
- (a) longest task per load step under 100 ms up to 2,000 rows, 1920 and 390@4x throttle: **live-checked, inconclusive on the absolute number, real improvement confirmed.** Headless Chrome, seeded 2,000-row account, production build (`vite preview`), scripted "scroll `main` to bottom repeatedly" driver with a `PerformanceObserver('longtask')`. Same driver, same final DOM (61,401 nodes both times): with `React.memo` reverted, longest task 608 ms / 78 long tasks / 781 MB heap; with the fix, 509 ms / 74 long tasks / 443 MB heap — an ~16% drop in longest task and a ~43% drop in heap, same direction as the ticket's own hypothesis, but the absolute number is well over 100 ms either way. The scripted driver forces `main.scrollTop = main.scrollHeight` every ~30 ms regardless of what has painted, which is far more aggressive than a real scroll and likely inflates both numbers versus the sweep's own measured baseline (437 ms for the production-build "last step," LED-125) — so this comparison shows the fix helps, not that it clears the 100 ms bar. See Backlog.
- (b) heap under 200 MB at 2,000 rows: **not met by this harness's number** (443 MB after the fix, down from 781 MB before) — same caveat as (a). See Backlog.
- (c) steady scroll unchanged: not separately re-measured; no code on the steady-scroll path changed (only mount-time memoisation and callback identity).
- (d) LED-125 numbers recorded before/after: recorded above, from this session's own driver, not the original sweep driver. See Backlog — the original numbers need the actual `browser-check-with-local-user.md` sweep driver rebuilt to compare apples-to-apples.
- (e) select-all, bulk actions and export still cover the full set: **PASS by inspection** — `bulkDeleteTransactions`, `bulkUpdateCategory`, `bulkCreateTransactions` and `exportMatch` all read `transactions`/`filtered`, not the windowed `rendered` count; none of this ticket's diff touches that path.
