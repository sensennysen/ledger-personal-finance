Branch `epic-22`, the single branch for the epic (owner, 2026-10-05). Six tickets: LED-257 to LED-262. Five commits, plus the validation fix and this retro. LED-261 needed no code.

## What was built
- **LED-257** (`e506d64`, fix `0cdb2f8`). Templates moved from the browser-wide `ledger_transaction_templates` key to `transaction_templates` (`id, user_id, name, fields jsonb, created_at`). RLS allows own rows only. The column is `fields` because `values` is an SQL keyword. `src/lib/transactionTemplates.ts` holds the versioned JSON (`v: 1`, never a date), the parser that skips and counts unreadable rows, and the conversion of the old key into rows that keep a valid uuid and date. `shouldUploadLegacy` uploads only into an account with no templates. The hook reads through `readWithPolicy`/`readAllPages`, uploads once with `upsert(..., { onConflict: 'id', ignoreDuplicates: true, defaultToNull: false })`, then removes the key. A failed upload keeps the key and is shown. Activity's strip uses `resolveLoadState` and `InlineLoadError`. Save and remove failures notify with Retry. `signOut` and `deleteAccount` remove the key.
- **LED-258** (`aa07d85`). The owner picked the `error_events` table as the sink. Rows are insert-only and own-rows-only; no select grant, so the operator reads them with the service role. `src/lib/errorReport.ts` strips numbers, quoted text, `=(…)` key values, e-mails and uuids from messages, ids from routes, and the message lines and URL queries from stacks. `shouldReport` is false for dev builds and local hosts. One page load sends each failure once, at most ten in all. `src/lib/reportError.ts` sends only with a session and never throws. The sources are `ErrorBoundary.componentDidCatch` (kind `boundary`, or `card` for Home widgets), window `error`, and `unhandledrejection`. The release is `VERCEL_GIT_COMMIT_SHA` (12 characters) through a Vite `define`.
- **LED-259** (`9da5e42`). The violation is Vite's dev client: after a dev server restart, `waitForSuccessfulPing` starts a `SharedWorker` from a `blob:` URL (vite 8.3, `dist/client/client.mjs`). Reproduced on the dev server right after "[vite] server connection lost". The production bundle's only `new Worker` is the Supabase Realtime heartbeat, which is off by default, and Ledger opens no channel. The policy is unchanged. Checklist C explains this and adds C5 (a signed-in console check on the live site).
- **LED-260** (`2c2e7e2`). The generator was already keyed per row: `dueRecurringPosts` plus `post_recurring_transaction` by id and flag. Only the one-off LED-232 backfill grouped by description. Tests pin that a rename changes nothing and that two rows sharing a description stay separate series. No code change.
- **LED-261** (no commit). `split_transaction` already inserts every line with `is_recurring = false` and no interval, and deletes the source. The retro's premise was wrong.
- **LED-262** (`af26bf4`). `set_transactions_updated_at` now has a `WHEN` clause: an update whose only change is `recurrence_next_posted` keeps `updated_at`. Every other update still moves it, including the flag set together with another column, and a no-op update.

## Issues
- **[BLOCKER, fixed]** The LED-257 upload failed with a 400 (`23502`, null id) when the old key mixed entries with and without a valid uuid. A bulk upsert sends the union of the keys and writes null for a missing one. The fix is `defaultToNull: false`. New pattern: `patterns/bulk-upsert-sends-missing-keys-as-null.md`. The pure tests could not catch it; only the browser run against local Supabase did.
- **Blocked approach.** Loading a test session into the app from a file was blocked by the permission classifier (credential leakage) during /apply. The seed's dev-only password form (prefilled, `import.meta.env.DEV` only) is the route that works; see `patterns/browser-check-with-local-user.md`.

## Backlog
- **Splitting the latest row of a recurring series ends the schedule.** The lines are not recurring and the source is deleted. Needs a product decision (LED-261 finding).
- **The old templates belong to whoever signs in first after the deploy** on a browser that held the shared key. Nothing in the key says whose they were. They go into that user's account if it has no templates; otherwise they are dropped.
- **Errors on signed-out pages are not reported.** `error_events` needs a session. Allowing anonymous inserts would let anyone write to the table.
- **The upload's error reads "Couldn't load your templates. Couldn't save this template."** when the upload, not the read, failed. Accurate but awkward.
- **Production checks after the merge:** LED-258 (b), a forced error shows as a row; LED-259 C5.
- **Migrations replayed from empty** only in CI. `pnpm db:reset` would have wiped the owner's local data.
- **A 400 on the dev login page** shows in the console before sign-in. Not investigated (it predates this phase; it was also seen in the epics 15-19 sweep).
- **Legal drafts** (storage notice row, Privacy Policy templates and error reports lines, data-deletion lines): the owner reviews them in the PR (OD-5).
