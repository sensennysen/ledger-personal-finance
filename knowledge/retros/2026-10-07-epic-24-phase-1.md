## What was built
- **LED-294** (`91d95c5`). Migration `20261007100000_loan_calculations_follow_rls.sql`.
  - `loan_purchase_paid_amount` and `loan_purchase_due_amount` are now `security invoker`, set with `alter function`, so the bodies are unchanged.
  - `revoke all … from public`. EXECUTE is granted explicitly to anon, authenticated and service_role.
  - The owner policies on `loan_purchases` and `loan_payment_allocations` now apply, so another user and anon get null.
  - The SECURITY DEFINER loan triggers call the helpers as their owner and still see every row.
- **LED-295** (`62dffab`).
  - `src/lib/authGeneration.ts` is pure: `begin(userId)` returns a token, `isCurrent(token, currentUserId)` checks it, and `invalidate()` drops every outstanding read.
  - `fetchProfile` checks the token after its read, and `moveBrowserSettings` checks it after every await. Only a current token may touch the profile state, the data copy, pending settings or the account.
  - A change of user invalidates outstanding reads and clears the profile at once. Sign-out and account deletion invalidate before forgetting the personal copies.
- **LED-296** (`0acae99`). Migration `20261007110000_card_payment_on_insert.sql`.
  - It adds `sync_card_payment_on_transfer_insert()`, an AFTER INSERT trigger on `transactions`, SECURITY INVOKER.
  - For a transfer into a credit card, it:
    - inserts the payment row with `on conflict (transaction_id) do nothing`;
    - calls `card_statement_shift`, which locks the card and applies a delta;
    - calls `card_statement_refresh_last`.
  - All of this happens in the same statement as the transfer.
  - The client steps are gone: `recordStatementPayment`, `recordGenerated`, `recordSynced`, `planStatementPayment`, the absolute paid-amount write and the Fix notice.
  - `createWithStatement`, `bulkCreateTransactions`, `generateDueRecurring` and AppLayout's synced listener now only call `notifyAccountsRefresh` and `notifyCardPaymentsRefresh`.
  - `rules/card-payment-is-a-transfer.md` points 1, 4, 6 and 7 are rewritten to match.

## Found
- **A denied function call segfaults local Postgres.** On `supabase/postgres:17.6.1.111`, any call to a function the role may not execute ends the backend with signal 11 instead of "permission denied". It happened for anon and for authenticated, and on a throwaway function too. Denied table reads raise normally.
  - The linked project records the same version (`supabase/.temp/postgres-version`).
  - Until LED-294 no function in `public` was denied to anon, because `revoke … from public` never removed Supabase's default grant to anon. So the path had never run.
  - If hosted behaves the same, a revoke would hand anyone a way to restart the database. LED-294 therefore keeps anon's grant and relies on RLS. See the note in `patterns/atomic-write-as-an-invoker-function.md`.
- **`revoke all … from public` does not revoke anon.** Every earlier "revoke from public; grant to authenticated" left anon able to execute: `card_statement_shift` showed `has_function_privilege('anon', …) = t`. These are all SECURITY INVOKER, so RLS still holds.
