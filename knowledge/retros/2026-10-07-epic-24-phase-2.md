# Epic 24 · Phase 2 — Offline write protection — retro (2026-10-07)

Branch `epic-24`, not pushed. Five tickets in build order: LED-297, LED-298, LED-299, LED-301, LED-300. One commit each, plus the validate fix and these docs. No migration and no release checklist B.

Owner decisions in /plan:
- **LED-299 takes option (A).** Queued items are versioned, and the drain confirms only the version it sent.
- **LED-297 uses an `updated_at` filter.** The conditional write is a PostgREST `.eq('updated_at', baseRevision)` in the same request, not a server function.

## What was built
- **LED-297** (`a003527`).
  - `QueueItem.baseRevision` holds the server's `updated_at` that the edit was made against. Updates and deletes are sent in one request filtered on it.
  - If zero rows come back, a re-read decides the outcome:
    - The row is gone: an update becomes conflict `deleted`, and a delete counts as synced.
    - The row is still there: conflict `edited`, with `serverSnapshot`.
    - The read fails: the item stays pending with `SERVER_CHECK_FAILED` and nothing is written.
  - Items without a revision (stored before this change) read first, then write against the revision they read. A failed check now keeps the item instead of writing blind.
  - `force` (Keep mine) is the only unconditional write.
  - `RevisionMoves`, `recordRevisionMove` and `rebaseRevision(s)` move later changes to a row onto the drain's own writes. They replace the `updatedRows` set.
  - Optimistic rows keep the server's `updated_at`. Before, they stamped `new Date()`, which made the next offline edit's base a guess.
- **LED-298** (`fcdf908`).
  - `bulkCreateTransactions` gives each row one ID, shared by the optimistic row and the queued insert.
  - A `23505` on `<table>_pkey` (`isDuplicateRowId`) re-reads the row by ID and owner (`reconcileInsert`). Our own row counts as synced once and fires `onSynced` once. Anyone else's ID is a countable failure.
  - Inserts return `id, updated_at`, so changes queued against a still-queued create take the insert's revision. `revisionFor(table, row)` gives such rows no revision at enqueue.
  - `unsentRows` makes an update or delete wait while its row's insert has not been sent.
- **LED-299 (A)** (`ffc1443`).
  - `QueueItem.version` is bumped by `editQueuedInsert`. The drain records `SentInsert { version, payload }`.
  - `mergeDrainResult(…, sent)` turns a newer version of a sent create into an update of the changed fields (`followUpUpdate`). If a kept insert was edited mid-drain, the newer copy wins.
- **LED-301** (`3ae6be9`).
  - After an upload, `setResolvedReceipt` writes the path to the stored item (no version bump). Only then is the local file removed. If that write fails, the local file is kept.
  - `processItem` catches its own errors and keeps the item as far as it got.
  - `uploadedReceipt` marks a file the drain uploaded. `discardFlagged` deletes it from storage, and so does a receipt replaced mid-upload.
  - `DrainClient.storage` gained `remove`.
- **LED-300** (`cbc9ccf`).
  - `isPendingReceipt` covers updates as well as inserts. An edit whose file is gone leaves the row's receipt alone (`withoutReceipt`). An edit with nothing left to send counts as synced.
  - `src/lib/receiptJob.ts` adds `splitPendingReceipt`. An online create or update whose upload fell back to the local copy saves the row without the marker, then queues `{ receipt_url: marker }` against the saved revision and drains.
- **Validate fix** (this commit). `itemNote` shows a pending item's `lastError` when it has no attempts, which is the check-failed case. Before, the queue sheet showed only "Edit · Transaction".

## Found
- **A row that is still a queued create has no server revision.** Its cached `updated_at` is the device's guess, so a delete or edit made against it would always conflict. `revisionFor` returns none, and the drain moves the change onto the insert's revision. This came up in /apply and was handled inside LED-298 because criterion (a) needs it.
- **A delete whose insert failed used to be dropped.** The delete read "gone", counted as synced, and the insert later recreated the row. `unsentRows` holds such changes. This predates the phase.
- **Showing a pending item's error is not automatic.** `itemNote` showed `lastError` only for `failed` items, so the new retryable message would have been invisible. Fixed in /validate.
- **The live drain runs under plain Node against local Supabase.** `queueDrain.ts` is pure, so a scratchpad script can pass the real supabase-js client. This gave real PostgREST evidence (timestamp filter round-trip, zero-row responses, the `23505` message) without a browser.

## Backlog
- **No way to open the queue sheet for pending items.** The banner opens the sheet only from Review, which needs a flagged item. A pending item kept by a failed check shows "Back online — 1 change still queued · Sync now" but not why. It is retained and retryable; showing the reason needs a design decision (22a).
- **Clock skew still matters for old items.** Items queued before LED-297 (no `baseRevision`) still compare the server's `updated_at` with the device clock. They drain out once, and new items are unaffected.
- **A pending receipt edit can be flagged.** If the user edits the same row again before the upload lands, the receipt-only edit is flagged `edited` and resolved with Keep mine. A field-scoped condition (`receipt_url` unchanged) would avoid this.
- **`bulkUpdateCategory` on queued creates.** It still queues a separate update for a queued create instead of editing the insert. It now works through the revision moves, but makes two writes.
- **Live checks used a stub, not a real network cut.** They used the `navigator.onLine` stub (pattern item 26). The offline CSV import screen was not driven in the browser.
- **The other-user duplicate ID** (LED-298) is unit-tested only. A live check needs a second user; LED-319 can carry it.
- **Pre-existing console error:** `Creating a worker from 'blob:…' violates … "worker-src 'self'"` appeared in the browser pane on the dev server. Not investigated; unrelated to the queue.
- **Phase 3 (LED-303):** the IndexedDB queue must keep `baseRevision`, `version` and `uploadedReceipt`, and the read-modify-write in `setResolvedReceipt`.
