# A card payment is saved as a transfer into the card

The database rejects an expense whose destination is not a loan (`enforce_loan_repayment_destination`), and `update_account_balance` credits an expense's `to_account_id` only when it is a loan. A payment to a credit card is therefore a `transfer` from the paying account to the card: no category, rate 1 (`cardPaymentTransfer` in `src/lib/cardPayment.ts`). Paid from another currency, it keeps `destination_amount`, what the card received, which the balance trigger and the statement steps credit instead (LED-269).

**Why:** LED-24 built the card form as "expense with a destination" and never saved one in a browser; the LED-113 retro found it could not be saved at all, and LED-146 moved it onto the working path.

**How to apply:**
1. The database records a card payment, not the client (LED-296). An insert trigger on `transactions` (`sync_card_payment_on_transfer_insert`) inserts the `credit_card_payments` row for any transfer into a credit card, moves the statement's paid amount with `card_statement_shift` (which locks the card, so concurrent payments both count) and points `last_payment_*` at the latest payment, all in the same statement as the transfer. A failure rolls the transfer back with it, and a replayed transaction id fails on the primary key, so a payment is never half-recorded or counted twice. Forms still save through `useCardPayment().createWithStatement`, which only tells the user about a queued payment and asks the card views to re-read. Never write the payment row or the paid amount from the client.
2. `transferCard(values, accounts)` says whether a save is one. Do not test `type === 'expense' && to_account_id` for a card.
3. LED-114 (OD-2 b) kept this model: no Card payments category and no migration. Because a card payment is a transfer, it stays out of every spending total, which all count `type === 'expense'` (`tests/cardPaymentSpending.test.mjs` pins it). Nothing may write an expense to a card, and a new spending calculation must filter on `type === 'expense'` too.
4. Recurring, imported and queued transfers to a card take the same path, because each is an insert (LED-190, LED-270, LED-193): `post_recurring_transaction`, the import's single insert and the queue drain all fire the insert trigger. `generatedCardPayment` and `importedCardPayments` only decide whether the card views need a refresh (`tests/recurringCardPayment.test.mjs`).
5. A payment row is linked to its transfer (`credit_card_payments.transaction_id`, LED-191). Triggers on `transactions` (`sync_card_payment_on_transfer_update` / `_delete`) move the history row and the statement's paid amount in the same statement as an edit or delete, so no client path has to remember. `shiftStatementPaid` mirrors `card_statement_shift`. Payments made before that migration are linked only when one payment and one transfer match exactly; the rest stay unlinked and an edit leaves their statement alone. An edit that makes a row a transfer into a card it was not paying (an expense switched to a transfer, or a destination moved onto the card) gets its payment row from the same trigger, with the statement shifted and `last_payment_*` pointed at the card's latest payment (LED-230); a queued edit gets it when it drains. An edit to a transfer that already went to the same card adds nothing, so an unlinked older payment is never recorded twice.
6. The paid amount is always moved by a delta on the locked card row, never written as an absolute figure from a copy the client held. Before LED-296 the client read the card and wrote the new total, and two payments could read the same paid amount and lose one increment; an Undo from an old closure once added to a stale paid amount (400 instead of 200 in the LED-191 live check).
7. A card or loan paid from another currency asks for the amount received (`needsAmountReceived`); the card presets and RepaymentAssist fill that field, since they are in the target's currency. A loan repayment is still an expense into the loan, credited and split by `coalesce(destination_amount, amount)` (`paymentCredit`, migration `20261006130000`). An import marks a cross-currency transfer with the other side's figure (`importTransferAmounts`), and an imported transfer into a card is recorded by the same insert trigger (LED-270, LED-296).
