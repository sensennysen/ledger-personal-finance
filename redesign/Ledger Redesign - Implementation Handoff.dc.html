Ledger — Design / Frontend

Navigation & UX Redesign — Implementation Handoff

Status: Ready for build · Date: 2026-09-09 · Companion visual reference: Ledger Redesign — Screens.dc.html

1 — What's wrong today, precisely

The app already carries M3 tokens and an M3-shaped nav (src/index.css, src/constants/colors.ts, BottomNav.tsx) from the earlier docs/M3_REDESIGN.md pass. It reads as a reskin, not as Material, for structural reasons color can't fix:

  • Bottom nav is a floating rounded card (rounded-t-[28px] in BottomNav.tsx) sitting off the screen edge. Real M3 navigation bars are flat, full-width, flush with the bottom edge — elevation comes from a tonal surface + hairline border, never a floating card with side gaps.
  • The add-transaction sheet is a dialog wearing a sheet's clothes. AppLayout.tsx renders one Base UI <Dialog> for three unrelated jobs (add / account menu / entry detail) and reshapes it into a bottom sheet on mobile via a CSS override (.m3-bottom-sheet fighting the dialog's own centered-transform classes). QuickEntry.tsx then mixes a custom numeric keypad with native <input type="date"> / note fields inside that fixed, max-h-[calc(100dvh-2rem)] positioned popup. When a native input focuses, the OS keyboard changes the visual viewport; the sheet is positioned off dvh and doesn't re-measure, so the focused field ends up hidden or the sheet jumps/resizes under the keyboard. This is the "buggy modal" — it's a positioning-model conflict, not a one-line fix.
  • Inputs, buttons and chips use generic rounded-rectangle styling (rounded-xl everywhere) instead of M3's shape scale, so nothing signals hierarchy — a text field looks like a button looks like a card.
  • No visible state layers. Interactive surfaces hard-swap background color on press instead of layering a translucent state overlay, which is most of why the UI feels flat/generic rather than Material.
  • Categories, Budgets, Reports and Settings are jammed into one hand-rolled "More" popover (fixed div + backdrop, not the Sheet primitive) — no focus trap, inconsistent active-state logic, and Budgets/Reports are two taps behind an unlabeled avatar tap.

2 — Principles for this pass

  1. Move off the gold seed — gold reads as premium/luxury, wrong tone for a self-hostable ledger. Rebuild the tonal palette from a new slate-blue seed (§2.5); keep Roboto/DM Mono and the rest of the shape/elevation system as-is.
  2. The add-transaction flow gets its own route, not a dialog. M3 explicitly specs a "full-screen dialog" for complex, keyboard-heavy forms for this reason.
  3. Every primary destination is one tap/click away, on both platforms, with the same five names.
  4. Settings and Categories are real pushed screens with a back affordance, not a menu bolted onto the avatar.

3.2 Desktop sidebar — grouped, with a pinned compose action

  • Two groups with an 11px uppercase label each: Main (Home, Transactions, Accounts, Budgets, Reports) and Manage (Categories, Settings).
  • A pinned, full-pill "+ New transaction" filled button at the top of the rail, under the logo — the desktop equivalent of the mobile FAB, always one click away regardless of which page is open.
  • Active item = full-width 44px pill, background: var(--accent) / color: var(--accent-foreground), replacing the current 2px-left-bar treatment.
  • Persist collapse state to localStorage (ledger-sidebar-collapsed) — currently local useState, resets every reload.
  • Avatar + name/email + sign-out stays pinned at the bottom, unchanged in function.

3.3 Top bar — both platforms

A slim sticky bar replaces the bannerless header: leading area (page title, or a breadcrumb like Settings / Appearance on nested routes), a search field/button that opens cross-month transaction search, and a sync-status affordance. On mobile only, the leading area is the avatar + greeting (opens the account sheet); on desktop the avatar lives in the sidebar instead.

4 — Add-transaction: a route, not a dialog

Replace the sheet === 'add' branch of AppLayout.tsx's dialog with two new full-screen routes, entered from the FAB / "+ New transaction" button:

RoutePurposeContent
/transactions/newStep 1 — type & amountTop bar: × close (left), title, "Next" filled pill (right, disabled until amount > 0). Body: segmented Expense/Income/Transfer control, DM Mono amount display colored by type, a custom 3×4 keypad (never the OS keyboard), and the 4 most-used category chips for that type so a typical entry never needs step 2.
/transactions/new/detailsStep 2 — everything elseTop bar: ‹ back, "Details", "Save" filled pill. Body: a small recap card (type · category · amount), then ordinary outlined fields — Account (select), Date, Note — plus "Attach receipt". This is a normal document-flow page: when Note focuses, the OS keyboard resizes the layout exactly like any other form, because there is no fixed-position sheet fighting it.
On mobile this is a full route push (slide-in from the right, matches the existing page-transition system); on desktop ≥1024px it can render as a two-step dialog instead, since desktop has no on-screen keyboard to conflict with. On success: pop back to whatever screen the flow was opened from and show a toast ("Expense added · View") — never force-navigate to /transactions (fixes defect #13 in docs/design-document.md §14).

Delete: the m3-bottom-sheet CSS override, the touch-drag-dismiss handler in AppLayout.tsx, and QuickEntry.tsx's role as a dialog child (its keypad/segmented/chip markup moves into the new step-1 route almost unchanged — it was already the right content, just trapped in the wrong container).

7 — Order of implementation

  1. Shape/elevation/state-layer token pass (§5) — no behavior change, immediately reduces the "reskin" feel.
  2. BottomNav.tsx flat bar + 5th item; Sidebar.tsx grouping + persisted collapse.
  3. TopBar.tsx (new) on both platforms.
  4. Add-transaction routes (§4) — the concrete bug fix. Delete the old dialog branch and .m3-bottom-sheet only once the new routes are wired and the FAB/pinned button point at them.
  5. Push Categories/Settings out of the "More" popover into routed screens with back affordances.
  6. Toast system for save/undo/sync feedback, replacing the forced navigate on transaction save.

8 — Strict sizing reference

Some elements drift when this spec gets implemented from prose alone. The values below are authoritative — hold to them exactly rather than eyeballing off the companion mockup. Every number is CSS px at 1x (this is a web app, not native dp); use only the spacing scale below, nothing in between.

Spacing scale: 4, 8, 12, 16, 20, 24, 28, 32, 40, 48, 56, 64px. Screen horizontal padding is always 16px on mobile, 28px on desktop content.

Nav and top-bar icons: 24px. List-row leading tiles: 40×40px @ 12px radius (mobile), 34×34px @ 10px radius (desktop dense rows). Inline small icons: 16–18px. Never introduce a fourth icon size.
